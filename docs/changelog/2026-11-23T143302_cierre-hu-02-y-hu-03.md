# Cierre de HU-02 y HU-03: salidas, precio y disponibilidad

- **Fecha:** 23 de noviembre de 2026, 14:33 (hora local)
- **Documento:** `entregables/Informe de Proyecto Formativo - Sistema de Gestión de Paquetes Turísticos y Reservas.pdf`
- **Páginas:** 21 (sin cambios; el trabajo no modifica el informe)
- **Alcance:** cierre de las historias HU-02 (fechas, capacidad y precio de
  las salidas) y HU-03 (consulta de disponibilidad), con la presentación de
  las salidas como tarjetas, la precarga del precio y el desglose de cupos
  para el personal.

## Antecedente

La ficha de salidas mostraba una tabla con pocos datos y el precio se
escribía desde cero, con un valor inicial de `1`. Además, el precio base
del paquete y el precio de la salida parecían duplicados, y la consulta de
disponibilidad no distinguía el desglose que el criterio de HU-03 reserva
al personal.

La revisión confirmó tres cosas:

1. el precio del paquete es de catálogo y el de la salida es el precio
   efectivo de esa fecha; pueden diferir por temporada, promociones, costos
   o tarifas de grupo;
2. la tabla de salidas no aprovechaba la información que ya existe en la
   base, como la ocupación y el precio base;
3. la vista de disponibilidad ya calcula pendientes y confirmados, pero la
   API no los exponía ni la interfaz los mostraba.

## Decisiones aplicadas

1. **Tres niveles de precio.** `paquete.precio_base` es el precio de
   catálogo; `salida.precio` es el precio efectivo de la fecha; y
   `cotizacion.precio_unitario` permitirá el ajuste por cliente o grupo.
   La salida conserva su precio como una foto: cambiar el paquete no altera
   las salidas ya programadas.
2. **Precarga del precio.** Al elegir un paquete, el formulario de salida
   completa el precio con su precio base y muestra la ayuda correspondiente.
   El usuario puede ajustarlo. Se documentó como `RN-SAL-21`.
3. **Tarjetas de salida.** La tabla se reemplazó por tarjetas con paquete,
   código, estado, recorrido, fechas, duración, ocupación, cupos
   disponibles, precio, precio base cuando difiere, punto de encuentro,
   observaciones y última actualización.
4. **Ocupación desde la vista.** La API de salidas devuelve
   `pasajerosOcupados` y `cupoDisponible` desde
   `vista_disponibilidad_salida`, sin almacenar un cupo duplicado.
5. **Desglose solo para el personal.** La API de disponibilidad entrega
   `pasajeros_pendientes` y `pasajeros_confirmados` solo a `ADMIN` y
   `PERSONAL`; el cliente recibe `null` y la interfaz no muestra esas
   columnas. La consulta del personal incluye la nota correspondiente.
6. **Estado agotado y formato.** La disponibilidad muestra una insignia
   «Agotada» cuando el cupo disponible es cero y formatea fechas y precios
   con el idioma de la aplicación.
7. **Pruebas de HU-02.** Se agregaron casos para impedir que la capacidad
   baje por debajo de los pasajeros reservados y para comprobar que el
   cambio de precio queda auditado en `historial_salida`.
8. **Cierre en el tablero.** `T-HU-02.1`, `T-HU-02.2`, `T-HU-03.1` y
   `T-HU-03.2` pasaron a `Hecho`.

## Cambios de contenido

### Reglas y diccionario

- Se agregó `RN-SAL-21` sobre el precio efectivo de la salida y su relación
  con el precio base del paquete.
- Se actualizó la trazabilidad de HU-02.
- La fila de `salida` en `bd/diccionario-datos.md` aclara que su precio
  puede diferir del precio base del paquete.

### Web

- La página de salidas usa una grilla de tarjetas responsive; la tarjeta
  vive en `app/components/salidas/Tarjeta.vue`.
- La API de salidas devuelve destino, duración, precio base, estado del
  paquete y ocupación.
- El formulario de salida usa `BaseCampoMoneda` para el precio y
  `UInputNumber` para la capacidad. El precio se completa con el paquete.
- La página de disponibilidad muestra el desglose de pendientes y
  confirmados solo al personal, la insignia «Agotada» y fechas y precios
  formateados.
- La API de disponibilidad decide el desglose según la sesión.
- Se agregaron los textos en español e inglés.

### Pruebas y tablero

- `bd/pruebas/reglas-paquetes.sql` cubre la capacidad menor que los
  reservados y la auditoría del cambio de precio.
- El tablero quedó con 40 tarjetas, 26 por hacer, 2 en curso, 0 en pruebas,
  0 listas para producción y 12 hechas.
- `make tablero-backlog` dejó el backlog y el CSV consistentes.
